# Durable-DAV — Background Worker

Scope: `apps/background/**`. Parent index: `../../AGENTS.md`.

- `src/index.ts` — re-exports `DavVolumeWorker`, `CronTasksWorker`, `CredentialVerifierDO` (also re-exported by `apps/api/src/index.ts` for DO bindings).
- `CredentialVerifierDO` (`src/dav/CredentialVerifierDO.ts`) — password-verification offload, `DAV_AUTH` binding, 32 shards via `credentialShardOf` (`shared`). **It accepts a presented password, so it must never be reachable from a public route** — stub binding only, and `fetch` rejects anything that is not `POST /verify` with a well-formed body. `POST /verify` in, `{ ok, needsRehash, upgradedHash }` out; the upgraded hash comes free with the verdict and removes a second derivation from the legacy-digest rehash. Holds **no storage**: the TTL cache is in-memory, so losing or evicting the object costs one re-derivation and nothing else. Caches **successes only** (a cached failure is a free verification oracle) keyed by `username` + password fingerprint, valued with the stored hash so a rotation invalidates. `blockConcurrencyWhile`-style single-flight per credential, so a cold-start burst of parallel requests runs one derivation rather than N. Sharding is load-bearing, not an optimization: a DO serializes its handlers, so one un-sharded verifier makes every concurrent authentication queue behind a single object.
- `DavVolumeWorker` (`src/DavVolumeWorker.ts`) — Facade over the WebDAV volume (one per bucket, `DAV_VOLUME.getByName(normalizeVolumeKey)`). Owns exactly three things: the error boundary, method dispatch, and the wiring from `dav/methods/*` to `DavRepository`/`DavLockGuard`/`DavConditionalGuard`. Everything else is a collaborator. Files at `/` over `createDofsFs` + metadata in DO SQLite (`dav_nodes/dav_props/dav_locks` via `ensureDavSchema`). No `blockConcurrencyWhile` nesting. Bucket deletion also clears bucket credentials in D1 (best-effort, FK cascades as backstop).
  - `ensureDavSchema` is likewise **once per isolate** (like `setDofsDeviceSize`), memoized on `schemaEnsured` and cleared on failure so a broken schema is retried rather than cached as done. It was previously re-run on every `sql()` call — 7 DDL statements plus an `ALTER` that throws and is caught, on *every* WebDAV request.
  - `setDofsDeviceSize` runs **once per isolate**, not per request, and a failure is logged rather than swallowed: `dofs.setDeviceSize` has no "already set" error, so any other failure silently left the per-volume quota unenforced, forever. The helper in `dav-store` therefore **propagates** — it used to catch and ignore, which meant this `ensureSize` log could never fire. `DavNodeInfo` carries no `contentLanguage` and the schema has no `content_language`/`displayname` column: nothing ever wrote either, and `displayname` is derived from the path. So `getcontentlanguage` is absent from every multistatus, which is conforming.
  - `COPY`/`MOVE` share one `deleteDestination` closure, so `COPY` inherits DELETE's descendant-lock scan instead of reimplementing DELETE minus it.
- `src/dav/` — `DavContext.ts` (pure `fsPathOf`/`hrefOf`/`resolveInnerPath` (`string | null`)/`stripBase` + `..` traversal rejection, `MAX_PATH_DEPTH`, and `DavBases { pathBase, hrefBase }` + `resolveDavBases` for the per-bucket href prefix mode) · `Base64` now lives in `@durable-dav/shared/utils` (allocation-light 3-byte-to-4-char codec, no spread/argument-limit; this file was the third copy of it) · `RangeParser.ts` (pure `parseRangeHeader`) · `davReadPolicy.ts` (the four `dofs` reads under one `ReadFailure` policy) · `DavRepository.ts` (SQL Repository: `statInner`/`requireStatInner`/`readMeta`/`nodeInfo`/`listChildren|Recursive`/`requireChildren|requireRecursive`/`listChildPage`/`countChildren`/`upsertFile|CollectionNode`/`copyMeta`/`delete|renameCascade`) · `DavLockGuard.ts` (lock-precondition Policy; single indexed `IN` query, **fails closed** on SQL error, 256-depth cap) · `DavConditionalGuard.ts` (RFC 7232 `If-Match`/`If-None-Match`/`If-Modified-Since`/`If-Unmodified-Since`) · `VolumeTransfer.ts` (the username-rename copy RPCs — not reachable from any `DAV:` method) · `methods/ReadMethods|WriteMethods|PropMethods|CopyMoveMethods|LockMethods.ts` (one Command per RFC 4918 family; `PUT` reads `MAX_FILE_BYTES` via injected `AppConfiguration` and caps the body through `readCappedBody` **before** buffering it).
- **Schema note — `dav_nodes.lock_null`**: added by `ensureDavSchema` (with an `ALTER` guarded on the duplicate-column error, since `CREATE TABLE IF NOT EXISTS` is a no-op on an already-provisioned volume; this is DO-local storage, not a D1 migration). The bit marks a resource that exists *only* to hold a lock, and `handleUnlock` releases it only when the bit is set — RFC 4918 §7.3 says a locked empty resource SHOULD NOT disappear when its lock goes away, and the same section says a lock-null resource and a zero-byte `PUT` are the same thing, so size cannot discriminate them. `upsertNode` takes `lockNull` explicitly and writes it on conflict too, so putting real content over a lock-null resource clears the flag.
- **RFC 4918 §7.6** — `renameNodeCascade` deliberately excludes `dav_locks`: "A successful MOVE request on a write locked resource MUST NOT move the write lock with the resource." Re-pathing the row carried a lock out of the collection it was taken on and onto a resource in a collection the locker never named. `deleteNodeCascade` still spans all three tables.
- **`dav/davReadPolicy.ts` owns how a failed `dofs` read is answered** (`ReadFailure` = `'degrade' | 'throw'`), and `DavRepository` is only named wrappers over it. This is the codebase's one fail-closed/fail-open decision, so it is a type in one module rather than a naming convention across eight methods — the convention had drifted once and a replication collection listing that degraded to `[]` queued the deletion of everything in it. **`require*` is the throwing policy**: `requireStatInner` (replication's per-path read), `requireChildren` / `requireRecursive` (lock enumeration, replication listing). Everything else is `'degrade'`. `ENOENT` is answered as "not there" under **both** policies, because `dofs` reports absence as a throw and a replication's first listing of a configured `remotePath` asks about a directory that has never existed — treating that as a fault fails every first sync. `listPage`/`countChildren` are `'degrade'`-only: a pager cannot report an error without inventing a total it does not have.
- **Lock enumeration for a decision uses `DavRepository.requireRecursive`**, which throws on a listing failure. `listRecursive` returns `[]` on failure, which is right for rendering a listing and wrong for "is any descendant locked" — a transient storage error would make "could not enumerate" indistinguishable from "nothing is locked", so DELETE and MOVE would remove a locked subtree.
- **Validate every header before mutating.** `COPY` used to validate `Depth` *after* recursively deleting the destination, so a request rejected with a clean `400` had already destroyed a subtree. Same class of bug as the quota check in `dofs.writeFile`.
- **`DavBases` is load-bearing.** `pathBase` (from `X-Dav-Base`, always the real `/owner/volume`) is addressing and feeds `resolveInnerPath`/`stripBase`; `hrefBase` (from `X-Dav-Href-Prefix-Mode`, `''` in root mode) is presentation and feeds only the href builders. Never collapse them back into one `base`: a `root`-mode bucket must still resolve its own request URL against the real base, or the whole bucket reads as empty rather than merely mis-anchored. `renderCollectionHtml` uses `pathBase` deliberately — its `<a href>` is browser-resolved, which §8.3 does not govern.
- `DavVolumeWorker` method map (RFC 4918 Class 1+2, ported from `r2-webdav`):
  - `OPTIONS` → `Allow` + `DAV: 1, 2`.
  - `GET`/`HEAD` → file bytes (Range via `dofs.read(offset/length)`, streams via `readFile`) or collection HTML browser; `404` missing, `206` partial.
  - `PUT` → `409` missing parent, `405` on collection, `413` over `MAX_FILE_BYTES`, `201/204`; stores `content-type` + `etag` in `dav_nodes`.
  - `DELETE` → recursive (`rmdir` + SQL cascade), `423` on locked descendants, `403` on volume root.
  - `MKCOL` → `415` with body, `405` exists, `409` missing parent.
  - `PROPFIND` → `207` multistatus (`allprop/propname/prop`, `Depth 0/1/infinity`).
  - `PROPPATCH` → atomic dead-prop upserts in `dav_props` (`403` on protected live props, `424` on partial).
  - `COPY`/`MOVE` → `Destination` same-volume check, `Overwrite`, `400` self/descendant, locks not copied but preserved on move.
  - `LOCK`/`UNLOCK` → exclusive/shared, `Depth`, `Timeout`, empty-body refresh, `423` conflicts, lock-null resources removed on unlock.
  - `OPTIONS` is answered **after** path validation but is a capability probe, not a content access.
- `CronTasksWorker` (`src/CronTasksWorker.ts`) — `POST /run` only (else `404`); single-flight (`202 Already running`); awaits `runScheduledTasks`. Triggered by cron `*/10 * * * *`.
- `src/scheduled/TaskRegistry.ts` — `CRON_TASK_FACTORIES` with `ExpiredCredentialPruningTask` (bucket-credential hygiene) and `ReplicationSyncTask` (scheduled two-way WebDAV replication); `runScheduledTasks` runs phase 1 then phase 2. **Replication adds no cron trigger** — it shares `*/10 * * * *` and slices its work, so a bucket syncing every 15 minutes and one syncing every week cost the same per tick. The planner is pure and lives in `backend-services` (`buildReplicationPlan`); this app owns only the I/O. `ReplicationRunner` is orchestration alone, and each of the three data-dangerous pieces has its own module that says so at the top: `collectSlice` (what could be seen, and the failure that closes the gate), `PlanExecutor` (the bytes and the post-pass base write), and `buildRemote` (every place a replication reaches outside itself — the sibling DO lookup, the egress allowlist, and the one secret decryption in the feature).
  - **`ReplicationSyncTask` must never throw.** `ReplicationRunner.runSlice` never throws either: one unreachable target cannot abort the other buckets in the same tick, so the outcome goes on the replication's row where the owner and the auto-disable counter both see it. A throw here would be attributed to the *task*, not to the target, and would take the credential prune down with it.
  - **The pass bookkeeping is `replicationPassSql`, not the DAO methods.** `pass_started_at IS NOT NULL` is the deletion gate: while a pass is open, an absence is not evidence of anything. It closes on a *failed* pass and on a *clean and complete* one, and stays open on a clean pass with work left. That third case was wrong first time round — clearing the column only on failure left it set forever, so a healthy replication never propagated a deletion at all.
  - **`VolumeReplicationRpc` bypasses `DavLockGuard` deliberately.** A lock is a client coordination device; replication is a principal with full write authority, and honouring locks would mean a sync silently skips whatever a desktop client happens to have open — the exact file an owner most wants backed up. Its filesystem mutators live in `replicaOperations`, which no `dav/methods/*` module imports, so a replication write can never satisfy a client's `ETag` precondition or ride in on a front-door request's authorization. The runner purges the read caches of *both* buckets after a pass: `DavReadCache` is invalidated by front-door methods, and a DO-RPC write reaches none of them, so without the purge the browser plane serves pre-sync bodies for the rest of the TTL — and reports a successful sync while doing it.
- **`dav_replica_state` is in `RENAME_CASCADE_TABLES` but deliberately not in `CASCADE_TABLES`.** A MOVE relocates the resource, so its base row relocates with it. A DELETE must *keep* the row: that row is the only evidence the deletion happened, and erasing it made the next pass see the path as new and pull the remote's copy back — resurrecting a deleted file while reporting `ok`.
- Composition: DO reads `AppConfiguration.fromEnv(env)` for `DO_DEVICE_BYTES`; no per-request DI container inside the DO (front resolves D1/auth before forwarding).
