# Durable-DAV — Backend Services

Scope: `packages/backend-services/**`. Parent index: `../../AGENTS.md`. Layer 3 (may use layers 0–2 only, never apps).

- Domain map:
  - `src/auth/AccessAuthService.ts` — `/user/*` identity: `DEMO_MODE` → `DEV_AUTH_EMAIL` → JWT (`cf-access-jwt-assertion` vs `TEAM_DOMAIN`/`POLICY_AUD`) → `ctx.access.getIdentity()` fallback. Never trust `Cf-Access-Authenticated-User-Email`.
  - `src/dav/VolumeCredentialService.ts` — bucket credentials (CalDAV-style): **PBKDF2-HMAC-SHA256 at 100 000 iterations** with a per-hash salt (constant-time compare; the legacy unsalted-SHA256 format is still accepted and reports `needsRehash` for the migration path), `MAX_CREDENTIALS_PER_VOLUME` (default 10), `DEFAULT/MAX_CREDENTIAL_EXPIRY_DAYS` (365/365); `createCredential(volumeId, volumeName, name, expiresInDays, readOnly)` generates `volume-adjective-animal-digits` username + `ddav_` password with 5x unique retry; `listCredentials/deleteCredential` scoped by volume id. `setCredentialReadOnly(volumeId, credentialId, readOnly)` flips the 0005 flag in both directions and touches nothing else — not the password, so it cannot be used to smuggle a new secret past the copy-once reveal; the volume scoping lives in the DAO's `WHERE`, and a row that is gone, expired, or owned elsewhere raises `NotFoundError` rather than reporting a flip that never happened. `readFlag` is the single coercion: absent means `false` (an old client keeps a working write credential), present-but-not-boolean is a 400, because quietly defaulting `"true"` to full access is the one outcome that must not happen by accident.
  - `src/dav/VolumeService.ts` — owner-only bucket CRUD by `(owner, name)` (case-insensitive): owner must match caller username, private-by-default (`isPrivate ?? true`), `updateVolume` (description + visibility + `hrefPrefixMode`, owner-only via `isVolumeOwner`), limits via injected `AppConfiguration` (`getMaxVolumesPerUser`, default 100, pure `VolumeCreatePolicy.checkVolumeQuota`); delete cascades bucket credentials. `createVolume` records the caller's **anchor** in `owner_email` and their account key in `ownerUserId`, and counts the quota by `owner_user_id` (an address-keyed count reads as zero after a change and would let the user exceed the cap). `requireCallerAccount`/`requireCallerUsername` fail **closed** — a missing account or handle throws rather than skipping the ownership check, which is the bypass that used to let any authenticated caller create buckets in any namespace.
  - `src/dav/VolumeCreatePolicy.ts` — `parseVolumePatch(input: VolumePatchInput): VolumePatch` is the **single** owner of the volume-write rules, shared by create and PATCH. Its parameter is the *unvalidated* shape (`unknown` fields) and it returns the narrowed one; typing the parameter as the already-valid `VolumePatch` is what let a wrong-typed body through, because the compiler then had nothing left to check. Type before value on every field, since each wrong type has a silent outcome: `"false"` for `isPrivate` reaches auth as **public**, a non-string `description` is stored verbatim into a `TEXT` column, and an unknown `hrefPrefixMode` either 500s on the `CHECK` or silently defaults to `base`. `MAX_VOLUME_DESCRIPTION_LENGTH` (500) applies on create as well as PATCH.
- **`resolveAccount` degrades only on `isMissingSchemaError`** (`accountLookup.ts`). The registry (`user_emails`) read is the one place a pre-0004 database is tolerated, and the degradation has to be *that specific*: the old bare `.catch(() => null)` also swallowed a transient D1 failure and fell through to `getByEmail`, which is the frozen-anchor lookup whose key is a re-registrable string. A revoked address (one whose account moved off it, so the registry correctly refuses to resolve it) then resolved against the *previous holder's* anchor, and that account's id became the caller's identity — full `/user/*` access from one failed `SELECT`. This is the fail-closed rule `packages/backend-data/AGENTS.md` states; `UserService.claimHandle`/`isHandleTaken` now follow it too (an unreadable `namespaces` table is pre-0004, an unreadable *row* is an outage, and the two must not be confused). `setPrimaryEmail` runs register → `setCurrentEmail` → revoke, matching `scripts/change-email.ts`: revoking first opens a window in which nothing authenticates if the next step fails.

  - `src/dav/DavPermissionService.ts` — `getRole(viewer: ViewerIdentity|null, volume)` → `admin|read|null`: owner implicit admin, public anon read, private hidden. No collaborators, no orgs. `viewer` is `{ userId, email }`; a raw address is no longer accepted, so the caller cannot pass the owner address to gain `admin`.
  - `src/dav/VolumeReplicationService.ts` + `replicationInput.ts` — owner-facing replication config. Owner-only by construction: every method takes a `volumeId` the route already resolved through `VolumeScopedRoute`'s guard, and there is deliberately **no credential-authenticated entry point** (see `apps/api`'s guide for why a bucket credential must never be able to name a target). `requireReplication` is scoped on `volume_id`, not looked up by id alone — without the scope, a caller holding any replication id could read another bucket's target URL and `last_error`, which on a deployment where targets are internal hostnames is enough to map private infrastructure. `mirrorDeletions` is resolved in `replicationInput.ts` (see below), so the service never stores a flag whose mode cannot read it. `replicationInput.ts` holds the whole request contract as pure functions: every field is `unknown` in, a narrowed value or a 400 naming the field out, so an unknown `mode` is a 400 rather than a `CHECK`-constraint 500 and `"false"` for `enabled` can never be a *silent* difference in who may read the target. `readMirrorDeletions(value, mode)` type-checks the boolean **and** resolves it against the mode it will be read in — validated on create against the mode stored in the same body (so `mode` + `mirrorDeletions` need not arrive in separate requests), on patch against the mode *after* the patch, and `true` outside `pull-only` is a **400** rather than a stored flag nothing reads. Moving off `pull-only` clears a set flag rather than leaving it dangling, since a later switch back would otherwise silently re-arm a destructive behaviour the owner had stopped using. The target is **absent from the patch input on purpose** — re-pointing mid-flight leaves the recorded base describing a tree that no longer exists, so a target change is delete-then-create, which also drops the base rather than comparing against a stranger's tree. `remotePath` rejects a leading `/` and any `..` segment instead of stripping them: a path that must be rewritten to be safe is one someone constructed to leave the configured root, and in `keep-both` mode, to delete there too. `REPLICATION_ENCRYPTION_KEY` is fail-closed — an unset key is a recorded failure, never an unencrypted fallback. **The sealed blob is `user:password` for `authKind: 'basic'`, composed by `sealableSecret` in `replicationInput.ts` and split on the *first* colon by `buildRemote`'s `authHeader` — one column, so the username travels inside the encrypted value.** That format was previously composed by *nothing*: both `createReplication` and `rotateSecret` validated that a username was present and then sealed the bare password without it, so every `basic` replication failed its first pass and the error's own advice ("rotate it") re-sealed the same broken blob. Two rules keep it from recurring: the writer and the reader are asserted **against each other** (`test/replication-credential.test.ts` drives the real service and decrypts what it stored; `test/integration/api/ReplicationCredential.int.test.ts` does it through the real route and the real D1 row), because a suite that hands the reader a hand-built envelope cannot catch a writer emitting the wrong shape; and `optionalSecret` does **not** trim, since RFC 7617 puts everything after the first colon into the password verbatim. `username` is re-sent on rotation rather than carried over — preserving it would mean decrypting the old credential to re-seal it, which fails exactly when an owner reaches for a rotation. Rows written before the fix cannot be repaired (the username was never stored anywhere): `scripts/replication-credential-audit.ts` lists them read-only.
  - `src/replication/` — the **pure** planner, with no `@durable-dav/webdav` dependency so the layer stays clean; `apps/background` owns the transports. `buildReplicationPlan(local, remote, base, { mode, trustAbsences })` is one function over three arrays, which is what makes the whole conflict policy testable without a server. `evidence.ts` holds every comparison it rests on, and each is conservative in the same direction: missing evidence answers "changed", because a false *changed* costs one redundant transfer while a false *unchanged* costs a lost edit. `provablyIdentical` only ever answers *yes* on positive evidence; `null` means "cannot tell" and the caller decides, never a silent match. `conflictWinner`'s mtime tiebreak is explicitly a tiebreak and not a guarantee (two clocks, and a remote an hour fast wins every argument) — when it cannot decide it returns `null` and the planner falls back to keep-both rather than picking, because a tie resolved by iteration order is the one outcome nobody could debug. **`pull-only` is decided by authority instead of by clock** (`copy-only` ⇒ local, `pull-only` ⇒ remote, never `null`), which is what makes it unreachable from the keep-both fallback and what makes `hashOnAmbiguous` meaningless there: both-sides-new means neither has a base, the remote already wins, and the local bytes are preserved either way. Its decisions are `pull` / `delete-local` / `pull-and-preserve` and never `push`, `delete-remote`, `keep-both`, or `compare-content` — `test/replication-pull-only.test.ts` asserts that as an invariant over an exhaustive 216-case state matrix, because a single upstream write reaching the executor would break the one thing the mode promises. `pull-and-preserve` is a separate decision kind rather than `keep-both` with `winner: 'remote'` for the same reason `keep-both` exists as a kind: the executors write to opposite sides, and reusing it would push a local edit to a target defined as unwritten. **`trustAbsences` gates every absence-based decision, not just deletions** — including `forget`: a failed listing makes one side look empty, so "absent from both sides" would read as "deleted everywhere", and acting on it drops the base row so the next pass pushes the remote's copy back over whatever is there. A conflict entry **states its `kind`** (`conflict` vs `deletion`) rather than letting the runner infer it from whether a copy was written; inference logged a `sync` conflict *resolved* by timestamp — which discards the loser and writes no copy — as a deletion, in the one place the feature promises to be trustworthy about what it destroyed.
- `src/dav/volumeOwnership.ts` — `isVolumeOwner(viewer, volume)`: the single ownership predicate, shared by `VolumeScopedRoute`, `VolumeService.updateVolume`, and `DavPermissionService`. `owner_user_id` decides when present; the frozen `owner_email` anchor is the fallback for a pre-0004 row, and a keyed row **never** falls back (a caller with an unknown id is refused rather than matched on a re-registrable string).
  - `src/user/UserService.ts` — `upsertUser(email)` returns `AccountSummary` and is **resolve-then-create**: the address resolves through the registry, so a user who changed address keeps their account instead of acquiring a second, empty one. Bootstraps a globally-unique `username` + `namespaces` claim (candidate derived from the *anchor*, so an opaque `anchor-…@users.invalid` account still gets a readable handle) and best-effort-swallows only that bootstrap — a resolution failure propagates, because an authenticated address with no account is not authorizable. Also `getProfileByEmail`/`getByUsername`/`renameUsername` (validates `USERNAME_PATTERN`, claim-first rename with self-reclaim, old names stay reserved; namespace self-ownership compares `user_id` with the anchor fallback).
  - `src/user/accountLookup.ts` — free functions `resolveAccount`/`resolveUserId`/`registerAccount` over `{ userDAO, userEmailDAO }`. One implementation shared by `UserService` and `UserIdentityService`. `registerAccount` **reads the anchor row back and requires its own generated id to be there**: `createUser` is `ON CONFLICT(email) DO NOTHING`, so trusting the generated id on a taken anchor points the registry at a phantom account and permanently strands the address (and makes the opaque-anchor retry fail too).
  - `src/identity/UserIdentityService.ts` — wraps `accountLookup` with a per-scope address→account memo, plus `resolveUserById` (inverse), `listAddresses`, `setPrimaryEmail`, `linkVerifiedEmail`. One memoized instance per request scope via `Tokens.UserIdentityService`; dependents resolve it from the container, never `new`. A **revoked** address resolves to null rather than falling through to an anchor lookup — otherwise a reassigned address would inherit the previous holder's account. `setPrimaryEmail` has **no route** on purpose: Access is the only authenticator, so a self-service change needs a proof-of-control confirm step first. The ops path is `scripts/change-email.ts`, which performs the same three statements in the same order (claim → move `current_email` → revoke others) so the user is never locked out.
- `src/composition/` — `Tokens` registry + `createRequestScope(env)` (`requestScope.ts` orchestrator; DAO tables in `daoBindings.ts`, service wiring in `serviceBindings.ts` + `serviceBindings/coreServices.ts`, shared env/factory in `serviceFactory.ts`): per-request `Container`, table-driven lazy+memoized DAO factories, lazy `AppConfig`. Handlers resolve `scope.get(Tokens.X)`.
- Constructor injection: every service takes `(env, deps?)` with `() => Promise<DAO>` factories defaulting to real DAOs — tests override with fakes (see `test/composition.test.ts`), no module mocks needed. `UserIdentityService` is the exception to "default to `new`": it is bound once per scope and shared, because its memo is the point. `VolumeService`'s own default holds **one** instance rather than constructing per call — it previously read `new UserIdentityService(env)` *inside* the factory thunk, which silently defeated the shared memo the composition root exists to provide. A service default must not re-allocate a collaborator the scope already owns.
- Address-vs-account discipline: anything that *decides* (ownership, permission, quota, dedup) takes the account key. Anything that *displays or authenticates* uses the current sign-in address. The frozen `users.email` anchor is read only for attribution and as the pre-0004 fallback.
- Errors via `@durable-dav/backend-errors` (`Bad/Unauthorized/Forbidden/NotFoundError`); time/ids via `@durable-dav/shared/utils` (`TimestampUtil`, `UUIDUtil`, `CryptoUtil`, `DavCredentialUtil`).
